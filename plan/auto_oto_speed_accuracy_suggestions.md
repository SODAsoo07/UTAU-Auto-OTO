# Auto OTO 개선 제안 (속도 + 오탐 감소)

## 목표
- 자동 OTO 지정 시간을 줄이되, 현재 품질 저하 없이 처리량을 높임.
- 자동 OTO 생성에서 음소/음절 오탐(잘못 매핑, 과한 점프, 저신뢰 행 반영)을 줄임.

## 1) 속도 개선 제안 (품질 유지 우선)

### 1-1. 파일 단위 병렬 처리(안전한 범위만)
- 현재 파이프라인은 파일별 독립 계산 비중이 높아, `TextGrid` 단위 작업을 병렬화하기 좋음.
- 권장: **정렬/기록 순서는 유지**하고, 내부 계산만 worker pool로 분산.
- 적용 후보:
  - 후보 추출/활성도 계산 (`core/oto_mapping_candidates.py`)
  - 점수 계산 및 인덱스 탐색 (`core/kr_mapping_scoring_v2.py`)
  - 행 스킵 판정 (`core/oto_row_abstain.py`)
- 기대효과: 파일 수가 많을수록 선형에 가까운 체감 단축.
- 품질 보호 장치: 결과 병합 시 기존 deterministic 정렬 키를 강제.

### 1-2. 반복 문자열 정규화/분해 캐시 확대
- 매핑 단계에서 문자열 분해/매치 함수 호출이 매우 잦음.
- 권장: alias 정규화, 음절 분해, match score 입력쌍에 대해 LRU 캐시 적용 범위를 확대.
- 근거: 생성기 모듈이 이미 `lru_cache`를 사용하고 있어(확장 여지 있음), 동일 패턴 반복 계산 절감이 가능.
- 기대효과: 대용량 배치에서 CPU 소모 감소.

### 1-3. 고비용 ML 보정의 선택적 실행
- 런타임은 backend(lightgbm/ensemble/coupled)를 로드하고 추론함.
- 권장: 1차 규칙 기반 결과가 고신뢰일 때는 ML 보정을 스킵하고, 경계 케이스에만 적용.
- 적용 기준 예시:
  - margin/row_confidence가 충분히 높고
  - blank_confidence가 낮은 경우는 skip
- 기대효과: 평균 추론 횟수 감소로 지연 단축.
- 품질 보호 장치: 스킵된 샘플 일부를 샘플링 재검증(오프라인)하여 회귀 감시.

### 1-4. 정렬(align) 단계의 증분 재사용 강화
- 이미 출력 폴더에 TextGrid가 있으면 정렬을 건너뛰는 경로가 있음.
- 권장: wav/text 변경 감지(해시/mtime)로 파일 단위 증분 정렬까지 확대.
- 기대효과: 재실행 시 정렬 비용 대폭 절감.
- 품질 보호 장치: 변경 감지 실패 시 전체 재정렬 fallback 옵션 제공.

## 2) 음소/음절 오탐 감소 제안

### 2-1. 저신뢰 행 차단(Abstain) 임계값을 format/alias 타입별로 세분화
- 이미 `decide_cv_row_abstain`에서 margin, row_confidence, blank_confidence 기반 스킵을 지원.
- 권장:
  - `cv`, `cv_head`, `vcv`를 동일 임계값으로 쓰지 말고 분리
  - glide 포함 음절은 더 보수적으로(min_margin 상향)
- 기대효과: 경계 케이스에서 잘못된 자동 확정 감소.

### 2-2. 음절 점프 규칙을 “이득 대비 위험” 기반으로 강화
- 현재도 `resolve_cv_syllable_index`에 jump 제한 및 best_gain 조건이 있으나, 환경별 편차가 큼.
- 권장:
  - forward jump 허용 시 `best_gain` + `vowel 일치` + `onset 유사` 3조건 동시 만족 가중 강화
  - glide 불일치 시 jump penalty 추가
- 기대효과: 인접 음절 오배치/한 칸 밀림 감소.

### 2-3. 후보 활성도(active) 판정에서 최소 지속시간을 데이터셋 기반 재보정
- 현재 active/vowel ms 임계로 후보를 걸러냄.
- 권장:
  - 화자/녹음세션별 분포를 보고 `min_active_ms`, `min_vowel_ms`를 profile화
  - 너무 짧은 비정상 구간(파열/잡음)을 더 강하게 제거
- 기대효과: 잡음성 후보 채택 감소.

### 2-4. 제외 사유 로그를 학습형 피드백 루프로 활용
- 스킵 사유(`row_low_margin_candidate`, `row_high_blank_confidence` 등)를 이미 수집 가능.
- 권장:
  - 사유별 Top-N alias를 주기적으로 집계
  - 임계값 조정 전/후 오탐률 변화를 AB로 추적
- 기대효과: 감(感) 조정이 아닌 데이터 기반 튜닝 가능.

## 3) 우선순위 실행안 (빠른 성과 순)
1. **임계값 세분화 + 점프 규칙 강화**: 구현 난이도 대비 오탐 감소 효과가 큼.
2. **ML 선택적 실행**: 품질 유지 조건만 명확하면 속도 개선이 즉시 체감됨.
3. **캐시 확대**: 안전하고 회귀 위험이 낮음.
4. **파일 단위 병렬화**: 효과는 크지만 동시성 이슈(로그/순서/결정성) 검증 필요.
5. **증분 정렬 고도화**: 재실행 사용자에게 특히 큰 시간 절약.

## 4) 측정 지표(변경 전/후 공통)
- 속도:
  - 총 처리시간, 파일당 평균 시간, ML 보정 호출 수
- 품질:
  - 수동 검수 기준 음절 오배치율, 음소 오탐율
  - abstain 비율(너무 높아지면 커버리지 저하)
- 안정성:
  - 동일 입력 재실행 시 결과 일치율(determinism)

## 5) 현실적인 리스크/대안
- 병렬화는 환경에 따라 I/O 경합으로 기대만큼 안 빨라질 수 있음.
  - 대안: 병렬 수를 CPU 코어의 50~75%로 제한하고, 우선 캐시/선택적 ML부터 적용.
- 임계값을 과도하게 올리면 오탐은 줄어도 누락이 늘 수 있음.
  - 대안: alias 타입별로 보수/기본 preset 2단계 제공 후 사용자 선택.
