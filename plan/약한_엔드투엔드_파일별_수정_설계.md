# 약한 엔드투엔드 파일별 수정 설계

## 1. 목적
- 현재 `coupled_nn_v1`의 장점을 유지한 채 `local raw mel encoder + 약한 엔드투엔드 hybrid`로 확장한다.
- 기존의 row 단위 supervision, `delta_*` 보정 구조, `confidence`, `aux`, `VC↔CV` pair loss, `wav_norm` holdout은 유지한다.
- 이번 설계는 full sequence end-to-end가 아니라, row 기준 onset/tail 주변 raw mel patch를 추가 입력으로 사용하는 `coupled_nn_v2_rawmel` 구현을 목표로 한다.

## 2. 목표 아키텍처

### 2.1 유지되는 요소
- `structured feature branch` 유지
- 기존 summary patch feature 유지
- 출력 타깃 유지
  - `delta_offset`
  - `delta_cons`
  - `delta_cutoff`
  - `delta_pre`
  - `delta_ovl`
- `confidence` head 유지
- `aux` head 유지
- `VC↔CV` pair loss 유지
- `wav_norm` holdout 유지

### 2.2 새로 추가되는 요소
- `onset raw mel encoder`
- `tail raw mel encoder`
- raw mel patch cache 로더
- runtime patch 생성 경로
- `coupled_nn_v2_rawmel` backend 메타/번들 규격

### 2.3 최종 모델 구조
- 입력 1: 기존 structured feature vector
- 입력 2: 기존 summary patch vector
- 입력 3: onset raw mel patch tensor
- 입력 4: tail raw mel patch tensor
- 구조:
  - `feature_net`
  - `patch_summary_net`
  - `onset_mel_encoder`
  - `tail_mel_encoder`
  - `joint fusion`
  - `delta_head`
  - `conf_head`
  - `aux_head`
- 출력은 기존 `v1`과 동일한 의미를 유지한다.

## 3. 서브시스템별 변경 책임

### 3.1 feature/row 식별자 계층
목표:
- dataset row가 raw mel patch cache를 안정적으로 참조할 수 있는 식별 키를 제공한다.

변경 책임:
- `core/oto_ml_features.py`
  - row마다 재현 가능한 `cache_key` 구성 필드 생성
  - patch anchor 계산값 노출
  - onset/tail patch 추출 기준이 될 시간값을 row에 넣는다

추가할 row 필드:
- `mel_patch_key`
- `mel_patch_debug_key`
- `mel_onset_anchor_ms`
- `mel_tail_anchor_ms`
- `mel_patch_source`

고정 규칙:
- `mel_patch_key`는 cache lookup 전용 안정 키
- `mel_patch_debug_key`는 사람이 읽기 쉬운 디버그 키
- `mel_onset_anchor_ms`는 1차적으로 `mel_offset_candidate_ms`, 없으면 `base_offset`
- `mel_tail_anchor_ms`는 1차적으로 `mel_cutoff_candidate_ms`, 없으면 `base_cutoff_abs`
- anchor 값은 ms float로 저장하되, cache key에는 직접 넣지 않는다

### 3.2 cache 생성 계층
목표:
- row별 onset/tail raw mel patch를 미리 추출해 `.cache/oto_ml_mel_patches/`에 저장한다.

변경 책임:
- 신규 helper 또는 서브모듈 추가
  - 권장 위치: `core/oto_ml/features/caches.py`에 확장하거나 raw mel patch 전용 모듈 추가
- 신규 CLI 추가
  - 권장 위치: `ml/scripts/coupled/build_mel_patch_cache.py`

필수 동작:
- dataset CSV를 입력으로 받음
- 각 row의 `wav`, `mel_onset_anchor_ms`, `mel_tail_anchor_ms` 기준으로 patch 추출
- shard `.npz`와 manifest JSON 생성
- dataset row 수와 cache row 수 검증

### 3.3 model 계층
목표:
- 기존 summary patch branch를 유지하면서 raw mel onset/tail encoder를 추가한다.

변경 책임:
- `core/oto_ml/coupled/model.py`

구현 결정:
- 기존 `COUPLED_BACKEND = coupled_nn_v1`는 유지
- 새 backend 상수 추가
  - `COUPLED_BACKEND_RAWMEL = coupled_nn_v2_rawmel`
- 기존 `_build_model(...)`는 `v1` 전용으로 유지하거나 wrapper로 남김
- 새 builder 추가
  - 예: `_build_model_rawmel(...)`

raw mel encoder 설계 고정:
- onset/tail encoder는 서로 동일 구조의 small CNN 사용
- 입력 shape: `[batch, 1, frames, mel_bins]`
- encoder 출력은 고정 길이 embedding
- 두 encoder는 weight sharing 없이 분리
- summary patch embedding과 structured embedding과 concat

권장 encoder 블록:
- `Conv2d -> ReLU -> Conv2d -> ReLU -> AdaptiveAvgPool -> Linear`
- 지나치게 큰 모델은 금지
- 초기 구현에서는 Transformer 사용 금지

### 3.4 training 계층
목표:
- CSV + raw mel cache를 함께 사용하는 학습 경로를 추가한다.

변경 책임:
- `core/oto_ml/coupled/training.py`

구현 결정:
- 기존 `train_coupled_bundle(...)`는 `v1` 경로로 유지
- 신규 엔트리 또는 옵션 추가
  - 권장: `train_coupled_bundle_rawmel(...)`
- DataFrame 기반 즉시 tensor 변환만으로 끝내지 않고, `Dataset/DataLoader` 경로를 추가한다
- batch 구성 요소:
  - structured feature tensor
  - summary patch tensor
  - onset raw mel tensor
  - tail raw mel tensor
  - target tensor
  - aux tensor/mask
  - base tensor
  - boundary tensor
  - sample weight

학습 규칙:
- loss 구성은 `v1`과 동일
- raw mel 추가로 인해 바뀌는 것은 입력만이다
- `pair loss`, `aux loss`, `align loss`, `constraint penalty` 모두 그대로 유지
- `group_column` 기본값은 계속 `wav_norm`

### 3.5 inference/runtime 계층
목표:
- `v2` bundle 추론 시 학습과 동일한 patch spec로 raw mel patch를 생성해 입력한다.

변경 책임:
- `core/oto_ml/coupled/inference.py`
- 필요 시 runtime 라우터 계층

구현 결정:
- `load_coupled_bundle(...)`는 `v1/v2` 모두 로드 가능하게 확장
- `predict_coupled_deltas(...)`는 `v1`과 `v2`를 분기 처리
- `v2`에서는 feature row만으로 충분하지 않고 raw mel patch도 필요하므로, patch 생성에 필요한 입력이 없으면 예측 실패로 처리
- 이 실패는 runtime 상위 계층에서 fallback 이유로 해석 가능해야 한다

필수 메타 의존성:
- `patch_spec`
- `mel_bins`
- `frame_hop_ms`
- `normalization`
- `rawmel_backend`

### 3.6 metadata 계층
목표:
- `v2` 모델이 어떤 patch spec과 cache spec으로 학습됐는지 번들에 완전 기록한다.

변경 책임:
- `core/oto_ml/coupled/training.py`
- `core/oto_ml/features/schema.py`

기록 필드:
- `backend: coupled_nn_v2_rawmel`
- `source_backend: coupled_nn_v1`
- `rawmel_enabled: true`
- `patch_spec`
- `mel_cache_version`
- `mel_bins`
- `frame_hop_ms`
- `onset_window_ms`
- `tail_window_ms`
- `normalization`
- `summary_patch_features`
- `wav_norm_holdout: true`

## 4. 파일별 수정 범위

### 4.1 `core/oto_ml_features.py`
추가 책임:
- row 식별용 안정 키 계산
- onset/tail anchor 계산
- runtime과 cache builder가 재사용 가능한 anchor 계산 함수 분리

구현 기준:
- 기존 row field 제거 금지
- 새 field는 append 방식으로 추가
- backward compatibility 유지

### 4.2 `core/oto_ml/features/schema.py`
추가 책임:
- raw mel variant 메타 필드 정의
- feature/cache version 규칙 확장
- dataset schema 설명에 raw mel 관련 row field 포함

구현 기준:
- 기존 `v1` schema 파괴 금지
- `v2` 전용 메타 필드는 optional 처리

### 4.3 `core/oto_ml/coupled/model.py`
추가 책임:
- `coupled_nn_v2_rawmel` 모델 정의
- onset/tail encoder 정의
- `v1`/`v2` 분기 가능한 builder 구조 제공

구현 기준:
- `v1` 모델 저장/로딩 호환 유지
- `v2`는 별도 payload 필드로 구분

### 4.4 `core/oto_ml/coupled/training.py`
추가 책임:
- raw mel cache 로더
- Dataset/DataLoader 경로
- `v2` 저장 메타 확장
- `v1`과 `v2` 공통 loss 재사용 구조 정리

구현 기준:
- 기존 `v1` 학습 진입점 깨지지 않게 유지
- raw mel이 없으면 `v2` 학습 시작 전에 명확히 실패

### 4.5 `core/oto_ml/coupled/inference.py`
추가 책임:
- `v2` bundle 로드
- raw mel patch tensor 추론 경로
- patch 부족 시 명확한 예외/실패 이유 반환

구현 기준:
- `v1` bundle은 기존처럼 feature row만으로 추론 가능
- `v2`는 patch 생성 필수

## 5. 명시적 설계 결정
- 새 backend 명칭은 `coupled_nn_v2_rawmel`로 고정한다.
- 구현 방식은 raw mel only가 아니라 hybrid 방식으로 고정한다.
- 기존 `PATCH_FEATURES`는 유지한다.
- 기존 `wav_norm` holdout을 유지한다.
- 기존 `VC↔CV` pair loss를 유지한다.
- onset/tail raw mel encoder는 small CNN으로 고정한다.
- 첫 버전에서는 center patch, Transformer encoder, full sequence encoder를 제외한다.

## 6. 실패 및 호환 정책
- raw mel cache가 없으면 `v2` 학습은 시작하지 않는다.
- runtime에 patch 생성 정보가 부족하면 `v2` 추론은 실패로 보고 fallback 한다.
- 기존 `v1` bundle과 `v2` bundle은 완전 분리 저장한다.
- `v1` 모델 로딩/추론 경로는 기존과 동일하게 유지한다.
- `v2` 성능이 미검증이면 운영 기본값은 계속 `v1` 또는 기존 coupled 라우팅 정책을 따른다.

## 7. 구현 완료 조건
- `v2` 학습/저장/로딩/추론 경로가 문서 기준으로 결정 완료 상태여야 한다.
- 문서만 보고 구현자가 파일별 책임과 인터페이스 결정을 추가로 하지 않아도 되어야 한다.
