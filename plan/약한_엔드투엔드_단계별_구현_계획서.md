# 약한 엔드투엔드 단계별 구현 계획서

## 1. 목표
- 현재 `coupled_nn_v1`을 유지한 채 `coupled_nn_v2_rawmel`을 추가 구현한다.
- 구현 범위는 `local raw mel encoder + weak end-to-end hybrid`까지로 제한한다.
- full sequence end-to-end alignment 설계는 이번 범위에서 제외한다.

## 2. 단계별 구현 순서

### 1단계: 데이터 계층 준비

#### 작업 내용
- row 식별 키 추가
- onset/tail patch anchor 계산 로직 추가
- raw mel patch extraction helper 추가
- cache builder CLI 또는 내부 엔트리포인트 추가
- cache manifest 및 shard `.npz` 저장 구현

#### 수정 범위
- `core/oto_ml_features.py`
- `core/oto_ml/features/schema.py`
- raw mel patch cache helper 모듈
- `ml/scripts/coupled/build_mel_patch_cache.py`

#### 성공 기준
- 샘플 bank 1개 이상에서 onset/tail patch cache 생성 가능
- 생성된 cache를 다시 읽어서 row 수, key 일치, shape 일치 확인 가능
- `mel_patch_key`, `mel_onset_anchor_ms`, `mel_tail_anchor_ms`가 dataset row에 일관되게 들어감

#### 실패 기준
- row 수와 cache row 수 불일치
- patch shape 불일치
- NaN/Inf 포함
- anchor 계산이 재현되지 않음

### 2단계: 모델 확장

#### 작업 내용
- `coupled_nn_v2_rawmel` backend 추가
- onset raw mel encoder 추가
- tail raw mel encoder 추가
- 기존 summary patch feature와 concat하는 hybrid fusion 구현
- 저장/로드 payload에 `v2`용 메타 필드 추가

#### 수정 범위
- `core/oto_ml/coupled/model.py`
- `core/oto_ml/coupled/inference.py`

#### 성공 기준
- forward pass 통과
- batch 단위 output shape가 `v1`과 동일한 의미로 유지됨
- `state_dict` 저장/로드 가능
- `v1` bundle과 `v2` bundle을 구분 로드 가능

#### 실패 기준
- `v1` 로딩 호환성 파손
- raw mel branch shape mismatch
- encoder output 차원 불안정

### 3단계: 학습 경로 연결

#### 작업 내용
- CSV + cache joint loader 구현
- `Dataset/DataLoader` 기반 batch assembly 추가
- 기존 loss를 `v2` 입력 경로에 연결
- `pair loss`, `aux loss`, `align loss`, `constraint loss` 유지
- `wav_norm` holdout 유지

#### 수정 범위
- `core/oto_ml/coupled/training.py`
- 필요 시 신규 dataset helper 모듈

#### 성공 기준
- 소규모 데이터셋에서 1 batch 이상 학습 가능
- 소규모 overfit 실험 가능
- 기존 손실 항목이 모두 계산됨
- raw mel cache 누락 시 학습 시작 전 명확히 실패

#### 실패 기준
- `v1` 학습 경로가 깨짐
- raw mel cache가 있는데도 batch assembly 실패
- `pair loss`/`aux loss` 누락

### 4단계: 추론 경로 연결

#### 작업 내용
- runtime에서 onset/tail raw mel patch를 학습과 동일한 spec으로 생성
- `v2` bundle 예측 경로 추가
- patch 생성 실패 시 fallback reason 표준화
- confidence/fallback 라우팅 유지

#### 수정 범위
- `core/oto_ml/coupled/inference.py`
- coupled runtime 라우팅 상위 계층

#### 성공 기준
- `v2` bundle로 단일 row 추론 가능
- runtime patch spec이 bundle 메타와 일치해야만 추론 진행
- `v2` 실패 시 `v1/lightgbm/base` 하향 동작

#### 실패 기준
- patch 생성 정보 부족인데도 조용히 잘못된 추론 수행
- fallback reason이 불명확함
- `v1` 추론 경로가 영향을 받음

### 5단계: 평가 및 회귀 검증

#### 작업 내용
- `v1` 대비 holdout MAE 비교
- confidence 분포 비교
- `offset`, `preutter`, `cutoff` 우선 평가
- 형식별 최소 1개 이상에서 개선 확인
- 성능이 미확정이면 운영 기본값 변경 금지

#### 평가 대상
- 한국어 `cv`
- 한국어 `cvc`
- 한국어 `cvvc`
- 한국어 `vcv`

#### 성공 기준
- 최소 한 형식 이상에서 `v1` 대비 핵심 지표 개선
- `v1` 대비 퇴행이 있는 경우 원인 분석 가능
- runtime fallback 동작 검증 완료

#### 실패 기준
- 어떤 형식에서도 이점이 없음
- confidence 분포가 불안정해 fallback 의존이 과도함
- 성능은 좋아졌지만 runtime 비용이 과도하게 증가함

## 3. 테스트 계획

### 3.1 Unit 테스트
- patch extraction helper
  - onset/tail anchor 기준 patch shape 일치
  - padding/잘림 규칙 검증
- cache key
  - 동일 row에서 재현 가능
  - 문자열 정규화 일치
- tensor shape
  - onset/tail 모두 고정 shape 보장
- model forward
  - `v2` 입력으로 `delta/conf/aux` output shape 검증

### 3.2 Integration 테스트
- cache 생성 -> 학습 -> bundle 저장 -> 추론 전 과정을 1개 샘플 bank로 연결
- manifest와 bundle의 `patch_spec_hash` 일치 확인
- raw mel cache 누락 시 예상된 실패 발생 확인

### 3.3 Regression 테스트
- `v1` bundle 로딩 영향 없음
- `v1` 학습 명령 영향 없음
- 기존 summary-only coupled 경로 영향 없음
- `lightgbm`/`base` fallback 영향 없음

### 3.4 Runtime 테스트
- patch 생성 성공 시 `v2` 추론 성공
- patch 생성 정보 부족 시 `v2` 실패 후 fallback
- bundle patch spec 불일치 시 `v2` 실패 후 fallback

## 4. Acceptance Criteria
- `coupled_nn_v1` 호환 유지
- `wav_norm` holdout 유지
- `VC↔CV` pair loss 유지
- raw mel branch 추가 후에도 기존 summary-only 입력 경로가 깨지지 않음
- `v2` bundle은 메타만으로 patch spec을 완전히 복원 가능
- `v2` 추론 실패는 명시적이고 fallback 가능해야 함

## 5. 구현 순서상 주의점
- 1단계 cache/row key를 확정하기 전에는 모델 구현을 먼저 진행하지 않는다.
- 2단계에서 `v1` builder를 수정하더라도 `v1` payload 호환성을 깨면 안 된다.
- 3단계에서 DataLoader 경로를 도입하더라도 `v1` 학습 경로는 유지한다.
- 4단계에서 runtime patch 생성 규칙은 cache manifest와 완전히 같은 spec을 써야 한다.
- 5단계에서 평가 전 운영 기본값 전환은 금지한다.
