# 약한 엔드투엔드 데이터 캐시 포맷 설계

## 1. 목적
- raw mel patch를 dataset CSV 안에 직접 저장하지 않고 별도 cache로 저장한다.
- 학습과 추론이 반드시 동일한 patch spec을 사용하게 한다.
- cache를 통해 `coupled_nn_v2_rawmel` 학습 비용과 로딩 비용을 통제한다.

## 2. 저장 위치 및 경로 규칙

### 2.1 루트 경로
- `.cache/oto_ml_mel_patches/`

### 2.2 하위 경로 규칙
- `language/format_type/cache_version/patch_spec_hash/`

예시:
- `.cache/oto_ml_mel_patches/korean/cvvc/v1/7f83b1a2/`

경로 구성 요소:
- `language`
- `format_type`
- `cache_version`
- `patch_spec_hash`

고정 규칙:
- `patch_spec_hash`는 아래 항목을 직렬화한 뒤 안정 해시로 생성한다.
  - `mel_bins`
  - `frame_hop_ms`
  - `onset_window_ms`
  - `tail_window_ms`
  - `normalization`
  - `onset_anchor_policy`
  - `tail_anchor_policy`
  - `padding_policy`

## 3. 캐시 단위

### 3.1 기본 단위
- row 단위 patch cache

### 3.2 최소 저장 항목
- `onset_patch`
- `tail_patch`

### 3.3 선택적 저장 항목
- `onset_mask`
- `tail_mask`
- `debug_anchor_ms`
- `wav_relpath`

이번 설계에서 필수는 onset/tail patch 2개다.

## 4. row 식별 키

### 4.1 cache key
목적:
- cache lookup용 안정 키

필드 고정:
- `language`
- `format_type`
- `voicebank_id`
- `wav_norm`
- `alias_norm`
- `occurrence_index`
- `row_index_in_wav`

직렬화 규칙:
- 위 필드를 문자열로 정규화 후 `|`로 연결
- 공백/대소문자/경로 구분자 차이를 정규화
- 결과 문자열을 `mel_patch_key`로 사용

예시 구조:
- `korean|cvvc|bank_a|sample01|a k|3|17`

### 4.2 display/debug key
목적:
- 로그/디버그/리포트용

필드 고정:
- `voicebank_id`
- `wav`
- `alias`
- `alias_norm`
- `occurrence_index`
- `row_index_in_wav`

규칙:
- 사람이 읽기 쉬운 문자열을 그대로 보존
- lookup에는 사용하지 않는다

## 5. tensor shape 표준

### 5.1 입력 shape
- onset patch shape: `[onset_frames, mel_bins]`
- tail patch shape: `[tail_frames, mel_bins]`

### 5.2 배치 입력 shape
- onset batch shape: `[batch, 1, onset_frames, mel_bins]`
- tail batch shape: `[batch, 1, tail_frames, mel_bins]`

### 5.3 첫 버전 기본값
- `mel_bins = 80`
- `onset_window_ms = (-80, +160)`
- `tail_window_ms = (-160, +80)`
- `frame_hop_ms`는 현재 멜 추출 hop과 동일한 값으로 고정

### 5.4 padding/잘림 규칙
- patch window가 wav 시작 전으로 넘어가면 앞쪽 zero padding
- patch window가 wav 끝 이후로 넘어가면 뒤쪽 zero padding
- 프레임 수가 초과하면 고정 길이로 자른다
- 학습과 추론 모두 동일 규칙을 적용한다

## 6. patch anchor 표준

### 6.1 onset anchor 정책
- 1차 기준: `mel_offset_candidate_ms`
- fallback: `base_offset`

### 6.2 tail anchor 정책
- 1차 기준: `mel_cutoff_candidate_ms`
- fallback: `base_cutoff_abs`

### 6.3 정책 이름 고정
- `onset_anchor_policy = mel_offset_then_base_offset`
- `tail_anchor_policy = mel_cutoff_then_base_cutoff_abs`

### 6.4 row 기록 필드
- `mel_onset_anchor_ms`
- `mel_tail_anchor_ms`
- `mel_patch_source`

`mel_patch_source` 값:
- `mel_candidate`
- `base_fallback`

## 7. 저장 포맷

### 7.1 고정 선택
- shard `.npz` + manifest JSON

### 7.2 이유
- Python/Numpy 환경에서 단순하게 읽고 쓰기 쉽다
- 디버그와 샘플 검증이 쉽다
- 첫 버전에서 추가 의존성을 최소화할 수 있다

### 7.3 shard 구성
각 shard 파일 예시:
- `patches_000001.npz`
- `patches_000002.npz`

각 shard 내부 배열:
- `keys`: string array
- `onset_patches`: float32 array
- `tail_patches`: float32 array
- `onset_valid`: uint8 or bool array
- `tail_valid`: uint8 or bool array

## 8. manifest 항목
manifest 파일명:
- `manifest.json`

필수 필드:
- `cache_version`
- `backend`
- `patch_spec`
- `patch_spec_hash`
- `mel_bins`
- `frame_hop_ms`
- `onset_window_ms`
- `tail_window_ms`
- `normalization`
- `onset_anchor_policy`
- `tail_anchor_policy`
- `padding_policy`
- `source_feature_version`
- `row_count`
- `shard_count`
- `created_at`

`patch_spec` 내부 필드 고정:
- `mel_bins`
- `frame_hop_ms`
- `onset_window_ms`
- `tail_window_ms`
- `normalization`
- `onset_anchor_policy`
- `tail_anchor_policy`
- `padding_policy`

## 9. 정규화 규칙
첫 버전 고정:
- `normalization = per_patch_log_mel_standardize`

정의:
- log-mel 기준으로 patch 추출
- patch별 평균 0, 표준편차 1 정규화
- 표준편차가 너무 작으면 epsilon 사용

주의:
- 정규화 규칙은 cache와 runtime에서 완전히 동일해야 한다
- 정규화 규칙이 바뀌면 cache를 재생성해야 한다

## 10. 무효화 규칙
아래 조건 중 하나라도 바뀌면 cache 무효화:
- `patch window` 변경
- `mel_bins` 변경
- `frame_hop_ms` 변경
- `normalization` 변경
- `onset_anchor_policy` 변경
- `tail_anchor_policy` 변경
- `padding_policy` 변경
- `row key` 규칙 변경
- `source_feature_version` 상승

권장 구현:
- `patch_spec_hash`가 달라지면 새 경로로 cache 생성
- 기존 cache는 삭제하지 않고 별도 보존 가능

## 11. 검증 규칙

### 11.1 row 수 검증
- dataset row 수와 cache manifest row 수가 일치해야 한다

### 11.2 shape 검증
- 모든 onset patch가 동일 shape여야 한다
- 모든 tail patch가 동일 shape여야 한다

### 11.3 값 검증
- NaN 금지
- Inf 금지
- zero-only patch 비율은 로그에 기록

### 11.4 missing patch 검증
- missing patch 비율 임계치: 0%
- 첫 버전에서는 onset/tail 중 하나라도 생성 실패하면 그 row는 cache build 실패로 본다
- 부분 허용 정책은 두지 않는다

### 11.5 anchor 검증
- anchor ms가 음수거나 wav 길이를 심하게 벗어나면 경고와 함께 row fail 처리

## 12. 학습/추론 연동 규칙
- 학습 시 `mel_patch_key`로 cache lookup
- 추론 시에도 동일 key 생성 규칙을 사용하지 않고, runtime patch는 직접 생성하되 manifest의 `patch_spec`와 완전히 동일한 규칙을 사용한다
- bundle 메타에는 학습에 사용한 `patch_spec_hash`를 반드시 기록한다
- runtime patch 생성 spec이 bundle과 다르면 `v2` 추론은 실패 처리하고 fallback 한다

## 13. 완료 기준
- 문서만 보고 구현자가 cache 경로, 키, tensor shape, shard 형식, manifest 형식, 무효화 규칙을 추가 결정 없이 구현할 수 있어야 한다.
